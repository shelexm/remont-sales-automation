# Диагностика очередей локального стенда

Чтобы вручную проверить очередь в работающем контейнере приёмника:

```sh
docker exec remont-trial-receiver-1 python -m app.diagnostics
```

Команда читает агрегированные числа из PostgreSQL в транзакции только для чтения. Она не выводит заявки, телефоны, ошибки провайдеров или секреты и не изменяет данные. `pending` и `processing` сами по себе нормальны: обработка и повторные попытки могут быть запланированы на будущее. `overdue` означает, что задание оставалось доступным дольше порога (по умолчанию пять минут), а `expired_lease` — истекшую аренду обрабатываемого задания. Порог меняется аргументом `--overdue-minutes` от 1 до 1440. Однократное обнаружение истёкшей аренды может быть временным: проверьте повторно.

Статус `attention` и код выхода 1 означают просроченные задания, истёкшие аренды, `failed` или `uncertain`. Код 0 означает отсутствие этих признаков на момент проверки; код 2 — ошибка подключения, схемы или аргумента. Запланированные на будущее повторные попытки не считаются просроченными. `uncertain` необходимо сверить с CRM или Telegram вручную: не повторяйте доставку вслепую, так как операция могла уже выполниться.

Команда проверяет только содержимое очередей в базе. Она не гарантирует доступность Tilda, туннеля, n8n, CRM или Telegram и не создаёт оповещений. Состояние контейнера приёмника отдельно видно в `docker inspect --format '{{.State.Health.Status}}' remont-trial-receiver-1`. При выключенном компьютере никакая проверка не выполняется. Для постоянного использования нужны внешняя проверка доступности и оповещения.

## Периодическая проверка в Docker

Необязательный сервис `monitor` запускается профилем Compose `monitor`, отдельно от остальных контейнеров. Перед запуском задайте в локальном env-файле `MONITOR_PUBLIC_HEALTH_URL=https://АДРЕС-ТУННЕЛЯ/health` и используйте те же env-файлы и Compose overrides, что и для рабочего локального стенда. После запуска базы и приёмника добавьте к обычной команде Compose `--profile monitor up -d --build --no-deps monitor`. Адрес — публичный URL проверки, без токена, query и личных данных.

Каждую минуту контейнер проверяет агрегаты очереди, внутренний `/health` приёмника и доступный извне HTTPS-адрес туннеля. В `docker logs remont-trial-monitor-1` появляются только изменения состояния. `docker inspect --format '{{.State.Health.Status}}' remont-trial-monitor-1` показывает `healthy` при успешных проверках и отсутствии проблем очереди; иначе — `unhealthy`. Истёкший результат старше 150 секунд также считается ошибкой. Если адрес не задан, будет `not_configured` и `unhealthy`. Исторические `uncertain` тоже сохраняют статус `unhealthy` до ручной сверки; это не обязательно текущая неисправность. Данные очереди не меняются.

При изменении адреса Quick Tunnel обновите `MONITOR_PUBLIC_HEALTH_URL`, пересоздайте `monitor` и отдельно настройте Webhook в Tilda. Проверка не проверяет форму и фактическое выполнение CRM/Telegram, не наблюдает n8n напрямую и не работает при выключенном компьютере. Сам Docker не перезапускает контейнер только из-за статуса `unhealthy`. Для контроля снаружи нужен отдельный механизм.

### Необязательные уведомления Telegram

В локальном env-файле задайте `MONITOR_TELEGRAM_ENABLED=true` и запустите монитор с `infra/local-demo/telegram-override.yaml` и существующим приватным env-файлом бота. Используется тот же бот и чат, что для тестовых заявок. Монитор получает токен и ID чата только через окружение; не публикуйте их и не выводите итоговую конфигурацию Compose. По умолчанию уведомления выключены.

Каждый тип проблемы подтверждается двумя последовательными проверками, после чего отправляется одно сообщение без персональных данных. О подтверждённом восстановлении ранее доставленного предупреждения отправляется отдельное сообщение. Состояние попыток хранится в томе `monitor-state`, чтобы перезапуск контейнера не повторял старые уведомления; запускайте только один экземпляр монитора. При отсутствии базы прежние проблемы очереди не считаются автоматически восстановленными.

Попытка фиксируется перед отправкой. При сетевой ошибке, неизвестном ответе Telegram или сбое после отправки она **не повторяется автоматически**: иначе возможно дублирование. Сообщение может потеряться, а восстановление неподтверждённого предупреждения не отправляется. В журнале и локальном статусе это видно как `alert_delivery: unconfirmed`; при отсутствии настроек или повреждённом состоянии — `unavailable`. Перед ручной сверкой не удаляйте том с состоянием: его удаление сбросит историю и может вызвать повторные уведомления. Когда Mac или Docker выключены, монитор не работает и не может сообщить о собственном отключении; канал Telegram также не сообщает о собственной недоступности. Это демонстрационный мониторинг, не гарантированная система оповещений.
