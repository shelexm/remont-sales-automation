# Интеграции: предварительная версия

После внутренней обработки события триггер добавляет отдельные задания CRM и Telegram. Обработчик `integrations` читает задания из PostgreSQL. Каждая доставка имеет статус, счётчик попыток, задержку и ограниченную аренду. Сообщения не содержат имени или телефона; технические ошибки хранятся как короткие коды.

## CRM

`CRM_PROVIDER=demo` — тестовый провайдер, сохраняет синтетическую CRM в таблице `demo_crm` и не связывается с внешней системой. Уникальная карточка задаётся `case_id`; повторная обработка обновляет её. Это не настоящая CRM. `CRM_PROVIDER=espocrm` — адаптер REST API с параметрами `ESPO_URL` (HTTPS), `ESPO_API_KEY` и `ESPO_ASSIGNED_USER_ID`. В EspoCRM нужен отдельный API-пользователь с правами создания и доступа к собственным Contact и Opportunity, а также текстовое поле `cAutomationKey` в каждой сущности. `ESPO_ASSIGNED_USER_ID` задаёт ID этого пользователя: адаптер назначает его ответственным, чтобы повторный поиск и привязка контакта работали при доступе только к своим записям. В тестовой EspoCRM 10.0.11 обязательность даты закрытия сделки отключена; для иной настройки укажите допустимую дату согласно процессу компании.

Бюджет заявки задаётся в рублях, поэтому адаптер передаёт `amountCurrency=RUB`; в CRM необходимо включить RUB. На локальном демо рубль задан также валютой по умолчанию и базовой валютой.

При новой заявке адаптер ищет видимый роли контакт по точному нормализованному телефону. Единственное совпадение используется повторно без изменения исходной карточки; для новой заявки создаётся отдельная сделка. Если совпадений несколько, обработка получает статус `uncertain` и не выбирает карточку автоматически. После ответа CRM `409` поиск повторяется; если однозначного доступного совпадения нет, обработка также останавливается как неопределённая. Роль, ограниченная собственными записями, не видит контакты других владельцев: скрытые совпадения необходимо разрешать вручную. Защита от одновременного создания зависит от настройки поиска дублей в CRM и отдельно не подтверждена нагрузочным тестом.

5 ноября 2026 года адаптер проверен на локальной EspoCRM 10.0.11 в Docker: две синтетические заявки одного клиента использовали один контакт и разные сделки, повторное выполнение использовало те же ID, стадия и валюта RUB прочитаны. В тесте HTTP использовался только внутри изолированной Docker-сети через тестовый транспорт; штатный адаптер по-прежнему требует HTTPS. Публичный HTTPS, связка с Tilda и реальные уведомления пока не проверялись. До исправления тест выявил несколько не назначенных контактных записей в локальной демонстрационной CRM; они сохранены и не представляют реальных клиентов.

При создании сущности адаптер записывает намерение в `crm_entities`, затем делает POST. При повторной обработке он сначала ищет технический ключ в CRM. Если результат предыдущего создания неизвестен и поиск ничего не нашёл, задача переходит в `uncertain` для ручной сверки. Это уменьшает риск дублей, но не гарантирует отсутствие дублей при нарушении уникальности ключа в CRM, рассинхронизации резервных копий или одновременной записи сторонних интеграций. В EspoCRM необходимо отдельно проверить ограничения уникальности и резервирование.

6 ноября 2026 года синтетическая заявка прошла через временный HTTPS-туннель в локальный приёмник, отдельный контейнер n8n обработал её вручную, а тестовый запуск адаптера создал контакт и сделку в локальной EspoCRM. Наличие обеих записей и валюты RUB проверено через CRM API. В этом тесте адаптер обращался к EspoCRM по HTTP только внутри отдельных сетей Docker; штатный адаптер требует HTTPS. Получение заявки из опубликованной формы Tilda, работа n8n по расписанию и Telegram этим тестом не проверялись. Стандартный Compose по умолчанию использует `CRM_PROVIDER=demo` и не отправляет заявки в EspoCRM автоматически.

7 ноября 2026 года выполнена отдельная локальная проверка: заявка с вымышленными данными отправлена из опубликованной формы Tilda по HTTPS, сохранена приёмником, автоматически обработана отдельным n8n по расписанию и доставлена в EspoCRM. Контакт и сделка проверены через API. Для теста на компьютере дополнительно настроен внутренний HTTPS-прокси с локальным доверенным сертификатом; между прокси и EspoCRM используется HTTP внутри Docker-сети. Эта конфигурация экспериментального стенда не входит в стандартный Compose проекта и не заменяет проверенный production-деплой. Временный туннель может изменить адрес или стать недоступным; Telegram не был подключён.

Другие CRM подключаются собственной реализацией `CRMProvider` и адаптацией очереди. Реализации amoCRM и Битрикс24 ещё нет; стоимость и наличие API зависят от их тарифов.

## Telegram

`TELEGRAM_ENABLED=false` по умолчанию. После создания собственного бота и чата задайте `TELEGRAM_ENABLED=true`, `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в локальном `.env`, не публикуйте их и не отправляйте в чат. Для проверки бот должен иметь право писать в выбранный чат. Ошибки `429` повторяются после указанного API срока и с ограничением числа попыток. При сетевой ошибке после отправки результат может быть неизвестен; задание переводится в `uncertain` для сверки, а не отправляется повторно автоматически.

7 ноября 2026 года владелец подтвердил получение уведомления о вымышленной заявке из Tilda и напоминания по ней в личном Telegram-чате. Для проверки напоминания время только этой тестовой заявки сдвинули на 61 минуту; стадия сделки была получена из EspoCRM. Три более ранние тестовые отправки имеют статус `uncertain` после сетевых сбоев; они не повторялись автоматически. Проверка не подтверждает стабильность временного туннеля или готовность работать с реальными клиентами.

## Напоминания и отчёт

Для тестового провайдера статус `demo_crm.status = 'new'` означает необработанную заявку. Через `FOLLOWUP_MINUTES` создаётся одно напоминание в Telegram; перед отправкой статус проверяется снова. Смена статуса в таблице требует отдельного интерфейса или SQL с ограниченным доступом. Для EspoCRM предусмотрено периодическое чтение стадии сделки: напоминание создаётся только при свежем статусе, совпадающем с `ESPO_UNPROCESSED_STAGE` (по умолчанию `Prospecting`), и статус повторно проверяется перед отправкой. Это работает только после настройки и проверки реальной CRM; название стадии следует уточнить в конкретной воронке. Ошибка чтения не считается подтверждением просрочки.

`demo_analytics` показывает только агрегаты: количество событий, карточек, новых записей и ошибочных или неопределённых доставок. Это техническая демонстрация, не аналитика продаж.

## Локальная конфигурация и ограничения

Скопируйте `.env.example` в `.env`, задайте локальные секреты и запустите `docker compose up -d --build`. Миграции новой базы выполняются контейнером Alembic; для старой базы без версии следуйте [руководству по миграциям](migrations.md). Пример не настраивает производственные привилегии и TLS; его нельзя публиковать в интернете.

При ошибках `failed` и `uncertain` требуется ручная проверка, журнал не содержит тела ответа или персональных данных. Интерфейс управления этими заданиями, полноценный журнал аудита, проверка реальных сервисов, контрольный тест восстановления и развёртывание EspoCRM — следующие задачи. Реальная CRM и Telegram не включаются автоматически.
