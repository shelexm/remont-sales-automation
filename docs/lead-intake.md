# Приём заявок: состояние разработки

Приёмник обрабатывает POST `/webhook/tilda` с `Content-Type: application/x-www-form-urlencoded` и заголовком `X-Webhook-Key`. Tilda позволяет задать ключ для передачи в заголовке; `test=test` получает `200` без записи. Контракт необходимо подтвердить реальной формой при её подключении.

Обязательные поля: `tranid` (идентификатор Tilda), `Name`, `Phone`, `Service` (русские названия из [инструкции Tilda](tilda/assembly.md), либо `cosmetic`, `capital`, `design`, `other`), `Area` (1–10000 целых м²), `Budget` (1–1000000000 целых рублей), `Consent` (`yes`, `1`, `true` или `on`). Телефоны поддерживаются только российские; значения без кода страны трактуются как российские. Классификация идёт по `HIGH_BUDGET_THRESHOLD` (демо-порог, по умолчанию 1 млн ₽). Порог и справочник услуг должны быть согласованы с владельцем до публикации.

Событие сохраняется в PostgreSQL до ответа `200`; повтор с тем же `tranid` и теми же нормализованными данными не создаёт новую запись. Другие данные с тем же `tranid` возвращают `409`. Ошибка базы — `503`, ошибки данных — `422`, неверный ключ — `401`. Технический лог приложения не содержит поля заявки. Данные хранятся в БД в открытом виде: защиту доступа, срок хранения, резервное копирование и удаление необходимо настроить до работы с реальными данными.

В базе есть атомарный захват с блокировкой строк, ограниченным числом попыток, временем аренды и токеном для отклонения запоздавших подтверждений. Подготовлен импортируемый workflow n8n: раз в минуту он захватывает одно событие и вызывает `process_lead`. Новые обращения с одинаковыми нормализованным телефоном и типом услуги объединяются в одну карточку в течение 24 часов от последнего обращения; это демонстрационное правило, его нужно согласовать с владельцем. `completed` означает только завершение этой внутренней обработки, а не отправку в CRM. При сбое аренда истекает, событие доступно повторно; после пяти попыток оно переходит в `failed`. Импорт и выполнение workflow проверены в отдельном контейнере n8n 2.46.6 с тестовой PostgreSQL в CI; в тесте расписание заменено ручным запуском. Получение из реальной формы Tilda ещё не проверено. Тесты локальной EspoCRM и ограничения описаны в [integrations.md](integrations.md); реальный Telegram ещё не проверен. Это не готовая к публичному запуску система.

## Локальный запуск

Скопируйте `.env.example` в `.env`, замените оба секрета длинными случайными буквенно-цифровыми значениями и выполните `docker compose up -d --build`. Сервис слушает только `127.0.0.1:18080`, существующий n8n не изменяется. `GET /health` проверяет только процесс, а не готовность PostgreSQL. Схему новой базы создаёт Alembic до запуска сервисов; для старого volume без версии см. [руководство по миграциям](migrations.md). Для текущего этапа используйте только тестовые данные.

Отдельный тестовый PostgreSQL можно передать через `TEST_DATABASE_URL` при запуске `python3 -m unittest discover -s tests -v`. Интеграционные тесты очищают таблицу `lead_events` в указанной базе: указывайте **только отдельную одноразовую тестовую базу**. Без этой переменной тесты БД пропускаются. CI поднимает отдельный сервис PostgreSQL.

## Workflow n8n

Импортируйте `workflows/process-leads.json` в отдельный n8n и привяжите обе PostgreSQL-ноды к отдельной учётной записи с минимально необходимыми правами. Workflow изначально не активен. Для локального n8n в другом Docker Compose понадобится отдельно согласованная сеть и настройка доступа к БД; опубликованного порта БД эта конфигурация не содержит. Вход — строки `pending`/просроченная аренда; выход — идентификаторы события и карточки и флаг дубля. Экспорт отключает сохранение результатов успешных и ошибочных выполнений; настройки инстанса и фактическое отсутствие ПД в журналах ещё необходимо проверить.
