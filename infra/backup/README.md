# Резервные копии баз и проверка восстановления

Команды ниже отдельно сохраняют PostgreSQL заявок, MariaDB и файлы EspoCRM, SQLite-базу локального n8n и его ключ. Копии снимаются в разное время и не являются согласованным снимком всей системы. Дополнительные файлы n8n, сертификаты, переменные окружения, настройки Tilda и Docker-конфигурация отдельно не копируются.

Архив может содержать персональные данные и секреты интеграций. Скрипт создаёт каталог с правами `0700` и файл `0600`, не выводит строки заявок и не перезаписывает старые файлы. Если каталог уже существует и доступен группе или другим пользователям, выполнение остановится. Права доступа не заменяют шифрование и защищённую копию на другом устройстве.

Из корня репозитория, указав свой контейнер и свои имена базы и пользователя:

```sh
python3 infra/backup/backup_postgres.py \
  --container remont-trial-db-1 --database remont --user remont \
  --output-dir ../backups/postgres
```

Команда выполняет `pg_dump` в формате custom, проверяет, что архив читается через `pg_restore --list`, публикует его без перезаписи и выводит SHA-256. База должна быть доступна для `pg_dump` внутри указанного контейнера. Сверяйте контрольную сумму при переносе; она помогает обнаружить изменение файла, но не доказывает его подлинность. При сбое скрипт удаляет только свой частичный файл; после аварийного завершения процесса такой файл может остаться в закрытом каталоге.

## Проверка копии

Передавайте только доверенный архив проекта: восстановление чужого SQL-архива может выполнять произвольный код в PostgreSQL. Для проверки используется **новый одноразовый контейнер PostgreSQL 17 без сети и без подключённых томов пользователя**. Скрипт не подключается к рабочей базе и не перезаписывает её:

```sh
python3 infra/backup/verify_postgres.py ../backups/postgres/ИМЯ_АРХИВА.dump
```

Проверка восстанавливает архив с остановкой при ошибке и сверяет наличие версии Alembic, функций очереди и триггера интеграций; выводит только количества событий, карточек и заданий. Эти проверки **не подтверждают полную работоспособность всех бизнес-сценариев** и не проверяют согласованность с внешней CRM. При завершении контейнер удаляется; если удалить его не удалось, скрипт сообщит его имя и о том, что данные могли остаться.

## Восстановление всей системы

Автоматическое восстановление поверх действующей базы намеренно не реализовано. Для реального восстановления необходимо остановить приём и обработчики, иметь согласованные копии PostgreSQL, EspoCRM и n8n вместе с их секретами и ключом шифрования, восстановить каждую в отдельное окружение и проверить интеграции. Состояние очередей и CRM нужно сверить до повторной отправки заданий, особенно `uncertain`: иначе возможны дубли сделок или уведомлений. Только после проверки составляется конкретный план переключения и отката.

Расписание, ротация, шифрование, хранение вне компьютера, копирование дополнительных файлов и проверка общего восстановления ещё не автоматизированы. Не удаляйте и не перезаписывайте текущие тома при проверке.

## Отдельная копия базы MariaDB EspoCRM

Команды используют переменные пользователя и пароля, уже существующие внутри указанного контейнера MariaDB; пароль не передаётся в аргументах процесса на компьютере. Имя базы обязано совпадать с `MARIADB_DATABASE` контейнера. Выполняйте из корня репозитория:

```sh
python3 infra/backup/backup_mariadb.py \
  --container remont-local-crm-db-1 --database espocrm \
  --output-dir ../backups/mariadb
python3 infra/backup/verify_mariadb.py ../backups/mariadb/ИМЯ_АРХИВА.sql
```

Дамп может содержать личные данные и секреты. Каталог ограничивается правами 0700, файл — 0600; существующие файлы не перезаписываются. `mariadb-dump --single-transaction` обеспечивает снимок транзакционных таблиц, но не гарантирует согласованность нетранзакционных таблиц или параллельных изменений схемы. Файл SQL сохраняется без шифрования. Проверка признака завершения и SHA-256 не заменяет восстановления и не доказывает подлинность; сверяйте хеш при переносе.

Передавайте на проверку **только доверенный архив**: восстановление SQL выполняет содержащиеся в нём команды. Проверка запускает новый контейнер MariaDB 11.4 без сети и пользовательских томов, восстанавливает SQL с остановкой при ошибке и выводит только число контактов и сделок. Затем одноразовый контейнер удаляется. Если удаление не удалось, будет выведено его имя: данные могли остаться. Проверка подтверждает чтение двух таблиц, а не работу интерфейса CRM или полное и согласованное восстановление проекта.

## Снимок SQLite локального n8n

```sh
python3 infra/backup/backup_n8n.py \
  --container remont-local-automation-n8n-1 --output-dir ../backups/n8n
python3 infra/backup/verify_n8n.py ../backups/n8n/ИМЯ_СНИМКА.sqlite
```

Команда использует SQLite Online Backup через `node:sqlite` внутри указанного контейнера, поэтому захватывает зафиксированные данные вместе с активным WAL без остановки n8n. Способ проверен с образом n8n 2.46.6; он не предназначен для n8n на PostgreSQL или другого расположения базы. В контейнере создаётся временный приватный каталог, который удаляется после снимка; при аварийном завершении или тайм-ауте проверьте `/tmp/remont-n8n-backup-*` внутри контейнера вручную.

Проверка открывает файл только для чтения, выполняет SQLite `integrity_check` и считает workflow и credentials, не раскрывая их. Это не запуск n8n и не проверка расшифровки credentials. База содержит чувствительные данные; файл не зашифрован, права 0600. **Ключ `N8N_ENCRYPTION_KEY` не входит в снимок:** его отдельное сохранение описано ниже. Без ключа после восстановления credentials не расшифруются. Файлы из `storage`, пользовательские узлы, env и версия образа в снимок также не входят. SHA-256 помогает обнаружить изменение, но не подтверждает подлинность.

Отдельная копия ключа из работающего локального n8n:

```sh
python3 infra/backup/backup_n8n_key.py \
  --container remont-local-automation-n8n-1 --output-dir ../backups/keys
```

Ключ сохраняется как файл с правами 0600 в каталоге 0700 и не выводится в терминал. **Файл содержит действующий ключ в открытом виде**: не публикуйте, не присылайте его и не добавляйте в Git. Права доступа не заменяют шифрование. Сохраните ключ отдельно от базы в надёжном зашифрованном хранилище и на другом носителе; локальная копия на том же компьютере не защищает от потери устройства. При смене ключа создайте новую копию и проверяйте её с соответствующим снимком. После аварийного завершения проверьте закрытый каталог на оставшийся `.partial`.

Для более глубокой проверки снимка и текущего ключа исходного контейнера:

```sh
python3 infra/backup/verify_n8n_restore.py ../backups/n8n/ИМЯ_СНИМКА.sqlite \
  --source-container remont-local-automation-n8n-1
```

Вместо работающего контейнера можно проверить сохранённый ключ, указав `--key-file ../backups/keys/ИМЯ_КЛЮЧА.key`. Файл должен принадлежать текущему пользователю, иметь права не шире 0600 и не быть символьной ссылкой. Указывайте либо `--key-file`, либо `--source-container`.

Проверка считывает ключ из выбранного источника, не выводя его и не помещая в аргументы команд. Она копирует снимок в новый временный том и запускает **только CLI** n8n 2.46.6 в контейнерах без сети: читает список workflow и проверяет расшифровку всех credentials. Расшифрованный временный экспорт находится исключительно внутри `tmpfs` проверочного контейнера, не сохраняется в пользовательском томе и не выводится. Затем тестовые контейнеры и том удаляются; при ошибке очистки будет показано имя оставшегося тома. Для снимка без credentials проверка ключа невозможна и команда завершится ошибкой. Проверка не подтверждает запуск workflow, сетевые интеграции или совместимость с другой версией n8n.

## Файлы EspoCRM

```sh
python3 infra/backup/backup_espo_files.py \
  --container remont-local-crm-crm-1 --output-dir ../backups/espo-files
python3 infra/backup/verify_espo_files.py ../backups/espo-files/ИМЯ_АРХИВА.tar
```

Архив содержит три каталога контейнера: `data`, `custom` и `client/custom`. В них могут находиться конфигурация, секреты и загруженные файлы; архив не зашифрован и доступен только владельцу (0600). Он создаётся на работающей CRM, поэтому файлы и база MariaDB могут относиться к разным моментам, даже если команда успешно завершилась. Для согласованной копии нужна отдельная процедура с приостановкой изменений.

Проверка читает содержимое архива, базовую структуру и окончание, но не извлекает файлы и не подтверждает запуск CRM, сохранность отдельных смысловых связей или безопасность произвольного архива. Используйте только доверенные архивы; не распаковывайте их поверх текущих томов. При восстановлении сначала подготовьте отдельное окружение, проверьте содержимое и совместимость файлов с базой и версией CRM.
